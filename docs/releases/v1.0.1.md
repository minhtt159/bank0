Security patch. Found while deploying 1.0.0 behind Envoy Gateway — the defect only exists relative to a specific proxy's behavior, which is why reading the repo in isolation never surfaced it.

## `trustProxyHeaders` had no correct setting behind an appending proxy

`clientIP` read the **left-most** `X-Forwarded-For` entry. That is correct only behind an edge that **replaces** the header — Cloudflare, via `CF-Connecting-IP`. A gateway running with `use_remote_address` (Envoy, nginx, Traefik) **appends** the true downstream address instead, so the left-most entry is whatever the client sent.

That left no safe setting on such a cluster:

| `trustProxyHeaders` | 1.0.0 behavior |
|---|---|
| `true` | the per-IP auth rate-limit key came from an attacker-written value. Rotate it per request and the credential-brute-force backstop never fires — **fails open**. |
| `false` | every request keyed on the gateway pod's IP, so all clients shared one bucket — **fails closed**, throttling everyone together. |

**Fixed:** `X-Forwarded-For` is now read **right-to-left**, `server.trusted_proxy_hops` entries in (default `1`, mirroring Envoy's `xff_num_trusted_hops`). The right-most entries are the proxy-authored ones a client cannot forge. `CF-Connecting-IP` still wins outright when present, since Cloudflare replaces rather than appends.

Chart value: `trustedProxyHops` (default `1`), wired into both Deployments.

**If you run behind a single in-cluster gateway** (Envoy, nginx, Traefik): set `trustProxyHeaders: true` and leave `trustedProxyHops: 1`. You get real per-client rate-limit keys. On 1.0.0 the only safe choice was `false`, which lumped every client into one bucket.

Count every proxy between client and pod: `1` for a single gateway, `2` for Cloudflare → tunnel → gateway if you rely on XFF on that path (though `CF-Connecting-IP` makes the count moot there).

## Chart: the HTTP→HTTPS redirect route rendered when it shouldn't

The redirect `HTTPRoute` rendered whenever TLS and `httpsRedirect` were enabled, regardless of whether either surface was exposed. In a bring-your-own-routes release (`gateway.create=false` with both surfaces unexposed) it rendered with an **empty `hostnames` list** — an HTTPRoute matching *every* host on that listener — parented to a Gateway the chart had never created.

It is now gated on `gateway.create` **and** at least one exposed surface. Workaround on 1.0.0 was `gateway.httpsRedirect: false`.

## Gateway modes, now documented

`docs/04-deployment.md` §3 spells out the three supported shapes: chart owns the Gateway, attach to a shared Gateway, or **bring your own routes** (`gateway.create=false` + both surfaces unexposed → the chart renders no Gateway API objects at all). The third is how api and portal get *different* `parentRef`s today — two platform Gateways, external and internal — without per-surface attachment in the chart.

## Upgrading from 1.0.0

Drop-in. No schema changes, no migrations, no config that must move. If you set `trustProxyHeaders: false` as a workaround, revisit it per the guidance above.
