Password lifecycle release. The trigger: the seeded bootstrap admin had **no supported way to change its own password**, so deployments were running on the credential published in this repository. Fixing that turned into the whole lifecycle, since the schema was being altered anyway.

## Upgrade first, then rotate

After upgrading, the seeded `admin` account is held on `/console/password` until it sets a new password — the console redirects every other screen there and the admin JSON API answers `403 password_change_required`. That is the intended first-run experience, not a fault.

The flag is set **only if the account still holds the seeded password**, so an operator who already rotated by hand is unaffected.

**Anything that automates a portal login as `admin`/`admin` must rotate first.**

## What changed

**You can now rotate an operator password.** `/console/password` — any staff member changes their own. Previously `POST /me/password` was client-surface only (JWT), the admin JSON API refused password writes by design, and the console had no screen: `psql` was the only path.

**A password change now revokes every session for that account, on both surfaces, including the caller's.** The portal previously revoked nothing at all (staff have no refresh tokens, and portal sessions slide their idle timeout on every request, so an intruder actively using one never aged out), and the client deliberately spared the caller's own session. Both surfaces re-authenticate afterwards.

**bcrypt truncation is closed.** Nothing capped password length, and bcrypt hashes only the first 72 bytes — a longer passphrase was silently truncated, so anyone knowing its first 72 bytes authenticated. Passwords are now 12–72 **bytes** (bytes, not characters: 25 three-byte runes already exceed the window), enforced in one function shared by password change and registration.

**Per-account login lockout.** 25 consecutive failures lock an account for 15 minutes. The rate limiter was per-IP only, which distributed credential stuffing walks straight past (NIST SP 800-63B Rev 4 §3.2.2). A locked account is refused exactly like a wrong password, so it is not an enumeration oracle. The window expires on its own — there is no admin unlock, deliberately, because a time-boxed lock cannot strand the only administrator.

**Admins can force a rotation.** A user's rail gains **Require password change**, which flags the account *and* signs it out everywhere — the "evidence of compromise" trigger, as opposed to a schedule. The rail also shows when the password was last set and whether the account is locked out.

## No password expiry, deliberately

NIST SP 800-63B **Rev 4** (final, 2025-07-31) §3.1.1.2: verifiers **SHALL NOT** require periodic password changes, and **SHALL** force one on evidence of compromise. Rev 4 hardened this from Rev 3's "SHOULD NOT" — forced rotation reliably produces predictable variations. OWASP ASVS 5.0 and the UK NCSC agree.

PCI DSS 4.0 §8.3.9 is the one framework still requiring 90-day rotation, and it is inapplicable twice over: cardholder-data scope (bank0 holds no card data), and it exempts MFA-protected accounts anyway.

Password history and composition rules are also deliberately absent, on the same authority.
